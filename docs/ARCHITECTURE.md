# Устройство игры

Текущий малый онлайн-стенд реализован на Python/SQLite и SSE+POST:
[ONLINE-V1](ONLINE-V1.md). Ниже сохранён исходный план расширенной архитектуры;
Node/TypeScript, WebSocket и PostgreSQL пока не внедрены.

Предлагаемая архитектура; зависимости ещё не установлены и версии не выбраны.
Перед реализацией проверить актуальные официальные документы выбранных библиотек.

## Части

- Клиент на TypeScript с 2D-рендерером: рисует изометрию, интерфейс и анимации,
  принимает мышь/касания. Кандидат — Phaser; выбор ещё не закреплён.
- Отдельный Node.js/TypeScript игровой сервер: проверяет движение, строительство,
  сделки, права и контракты. Постоянное соединение WebSocket.
- PostgreSQL: персонажи, город, здания, предметы, денежный журнал и контракты.
- Статические изображения и звуки доставляются браузеру по HTTPS.

Первый сервер — один процесс и один город. Не начинать с микросервисов,
кластеров и распределённого рынка. Сначала измерить реальную нагрузку.
Постоянный RP-город сложен прежде всего согласованностью данных и правилами,
а не количеством10 подключений. Малый онлайн не гарантирует отсутствие затрат.

## Пример действия

Клиент отправляет: «персонаж хочет построить дорогу на клетке» с ID запроса.
Сервер сам проверяет роль, расстояние, участок, инвентарь и контракт. В транзакции
меняет материалы, объект и журнал. Только после успеха сообщает результат
всем подключённым игрокам. Клиент не назначает сам себе деньги и готовые дома.

Позиции передаются регулярно с интерполяцией; сделки и строительство —
события с подтверждением. При переподключении клиент получает снимок нужной
области. БД не нужно обновлять60 раз в секунду ради каждого движения.

## Постоянный мир

Время города хранится на сервере. При отсутствии людей можно приостанавливать
дорогую симуляцию и при входе считать ограниченный прошедший интервал.
Не накапливать бесконечные пожары/голод/долги за время отсутствия игрока.
Точные правила офлайн-работы и продолжительность суток предстоит выбрать.

Развитие до многих жителей: загрузка участков карты и рассылка только ближайших
изменений; затем измерения, профилирование и при необходимости несколько процессов.
Текущий проект не обещает будущую MMO без переработки.

## Объяснения по этапам

Для каждого шага показать Михаилу одно действие, одно сетевое сообщение и
изменение данных. Объяснять, какой процесс работает на VPS, что скачал браузер,
что остаётся после закрытия вкладки. Установка клиента для первой версии не нужна;
PWA и приложения рассматриваются позднее по реальной необходимости.

Деплой, службы, firewall и production — только отдельным согласованным этапом.
